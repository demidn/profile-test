# Professional Profile API

Тестовое задание - небольшой backend для профилей кандидатов на NestJS, GraphQL, Prisma и SQLite. Проект предназначен для демонстрации и тестового задания.


## Возможности

- получение профиля по slug;
- список профилей;
- links, experience, projects и skills;
- общие skills между профилями;
- двунаправленный GraphQL-граф `Profile -> Skill -> Profile`.

## Архитектура

```text
GraphQL resolvers
    -> application use cases
        -> infrastructure ProfileRepository
            -> Prisma
                -> SQLite
```

Здесь за некоторую базу взята Clean Architecture но я бы всё-таки описал как layered architecture с разделением ответственности. Domain-модели не зависят от GraphQL и Prisma. `ProfileRepository` находится в infrastructure, выполняет запросы и преобразует persistence records в domain-модели. GraphQL presentation явно преобразует domain-модели в GraphQL-модели.

Здесь как раз хотел бы уточнить про использование Repository - мне это кажется важным моментом. По логике чистой архитектуры - в слое application у нас лежат интерфейсы портов а в инфраструктуре реализации интерфейсов которые потом можно подставить например через DI. Но задумаемся какой именно профит это может принести самому приложению - выглядит красиво и описывается красиво - вот мы полностью не зависим от реализации, захотели подменили, вдруг понадобилось переписать под другое хранилище - мы легко в DI заменили - звучит красиво, тут не спорю - разделение ответственности и все такое.
Но вернемся к практике - нам нужно на каждый порт написать интерфейс, отдельно написать реализацию, отдельно сконфигурировать DI - все это увеличивает время разработки а значит деньги которые тратит бизнес, но есть ли здесь business value?
Если нам нужно подменить реализацию условно в тестах - это можно легко сделать и так - имея просто репозиторий с декоратором Injectable. Если мы вдруг решим что нам надо переписать на другое хранилище - и в том и в другом случае мы будем писать новые репозитории скорее всего новые мапперы и т. д. - то и здесь мы не получаем профита - наша самая главная фишка - а именно разделение на слои с бизнес-логикой, уровнем хранилища, уровнем презентации реализована. Кроме того вероятность что вдруг нам придется переписывать проект на другую репу - по моему опыту крайне мала, и чаще если и есть рефакторинг он затрагивает гораздо большую часть приложения.
По итогу когда нам может пригодиться интерфейс и реализация - когда у нас скажем в рантайме в разных местах под один интерфейс могут подставляться разные реализации - тогда здесь появляется и логика и ценность - но это опять же довольно редкие случаи и должны применяться только когда они реально применяются - а делать лишние интерфейсы и использовать подходы "по книжке" - в данном случае лишь приводят к большей потери времени. Здесь главное что мы готовы к такому повороту и безболезненно можем его ввести при необходимости.

Небольшой коммент про поля `Profile.skills` и `Skill.profiles` - они загружаются отдельными `@ResolveField`. Сделано это в общем больше для демонстрации возможности graphql и именно демонстрации запроса графа например такими квери
{
  profile {
    id
    skills {
      id
      name
      profiles {
        id
        name
      }
    }
  }
}

в данном тестовом задании вполне можно было реализовать их также как и остальные поля - хотя именно skills в данном случае несет большее бизнес-значение - проекты, опыт обычно относятся к конкретному разработчику а по скиллам можно найти профили разработчиков именно с этим скиллом

Но, опять же, отступая - тестовое задание было на выборку одного профиля и должно это быть одной проф страницей - тут я немного расширил изначальную задачу чтобы было поинтереснее

## Почему SQLite

Dataset небольшой и read-oriented, поэтому для локального запуска и Docker не требуется отдельный PostgreSQL. Prisma остаётся ORM, а SQLite упрощает воспроизводимый demo setup.

## Локальный запуск

Требуются Node.js 22 и pnpm.

```bash
cp .env.example .env
pnpm install
pnpm start:dev
```

Переменные окружения:

```env
DATABASE_URL="file:./data/app.db"
PORT=3000
CORS_ORIGINS=http://localhost:5173
```

`db:init` применяет Prisma migrations и запускает идемпотентный seed. Seed создаёт два демонстрационных профиля и переиспользует общие Skill-записи.

## Docker

```bash
docker-compose up --build
```

При старте контейнера создаётся каталог SQLite, применяются migrations, запускается seed, затем NestJS. Persistent volume намеренно не используется: при пересоздании контейнера demo database может быть создана заново.

## GraphQL

Endpoint: `http://localhost:3000/graphql`. Apollo Sandbox доступен через этот endpoint в режиме разработки.

Получить профиль:

```graphql
query {
  profile(slug: "demid-nikitin") {
    id
    slug
    name
    description
  }
}
```

Получить список профилей:

```graphql
query {
  profiles {
    id
    slug
    name
  }
}
```

Обойти граф профилей и навыков:

```graphql
query {
  profile(slug: "demid-nikitin") {
    name
    skills {
      name
      profiles {
        slug
        name
      }
    }
  }
}
```

Для неизвестного slug GraphQL возвращает ошибку с кодом `PROFILE_NOT_FOUND`. Внутренние Prisma details и stacktrace клиенту не передаются.

## Тесты

```bash
pnpm test
pnpm lint
pnpm build
```

Integration/e2e suite поднимает реальное NestJS-приложение, применяет migrations и seed к отдельной SQLite database, затем проверяет profile, profiles, граф `Profile -> Skill -> Profile` и ошибку отсутствующего профиля.

## Scope

Это demo assignment. В проект намеренно не включены authentication, DataLoader, PostgreSQL, persistent Docker volume и production observability. Эти решения соответствуют масштабу задачи.
